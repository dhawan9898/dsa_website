Contiguous Memory · O(1) Indexing

Arrays & Memory

Why indexing into an array is O(1): it's one multiplication and one addition, no matter how big the array is or which index you ask for.

Notes

An array is a block of memory just large enough to hold every element, back to back, with nothing in between — that's what contiguous means. Because every element is the same fixed size (an int is always 4 bytes, say), the computer never has to search for element i: it can compute exactly where that element starts with one multiplication and one addition — address = base + i × elementSize — and jump straight there. That single piece of arithmetic, not a search, is the entire reason array indexing is O(1): it costs exactly the same whether i is 0 or 999,999, and exactly the same on an array of 10 elements or 10 million.

Implementation: the demo below makes that formula concrete instead of abstract — watch the exact address get computed for a few different indices, including the very last one, and notice it's always the same one-step arithmetic. This is also why arrays can't grow: the memory right after the last element might already belong to something else, so "adding one more slot" isn't possible in place — it means allocating an entirely new, bigger block and copying everything over.

Stack vs. heap: a fixed-size local array like int arr[10]; is allocated on the call stack — fast, automatic, and freed the instant the function returns, but its size has to be known at compile time and it can't outlive the function. A dynamically-sized array via malloc(n * sizeof(int)) lives on the heap instead: its size can depend on a runtime value, and it survives until explicitly freed — which is also the risk, since nothing frees it automatically. Forgetting to is a memory leak; freeing it and using it anyway is a dangling-pointer bug, the same class of mistake covered on the Pointers in C page.

When it breaks: C never checks array bounds for you. Reading or writing arr[n] on an array of size n doesn't raise a clean error — the address formula still computes a valid-looking address, it's just one element past the block C actually gave you, so the read or write silently touches whatever memory happens to sit there next. That's undefined behavior: sometimes it does nothing visible, sometimes it corrupts an unrelated variable, and sometimes it crashes the program much later, far from the line that actually caused it.

One more thing Big-O deliberately can't see: because array elements are contiguous, reading them in order lets the CPU pull a whole neighborhood of them into fast cache memory at once, so later reads in that same walk are often almost free. A linked list traversal is the same O(n), but its nodes can be scattered anywhere in memory — same Big-O, often meaningfully slower in practice. Big-O counts operations, not memory layout.
