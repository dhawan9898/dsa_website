First In · First Out

Queue

A line at a counter: you join at the back and leave from the front. Whoever waited longest is served first.

The idea, in one picture

Picture the line at a coffee shop. New people join at the rear. The person at the front — who has waited longest — gets served and leaves next. Nobody cuts in, and nobody is served out of order. A queue is exactly this: a collection where you add at one end and remove from the other.

That rule is called First In, First Out, or FIFO — the exact mirror of a stack's LIFO. A stack touches one end for everything; a queue uses two ends, one to join and one to leave, so things come out in the same order they went in.

Three moves. Enqueue = add a value at the rear. Dequeue = remove (and return) the front value. Peek / Front = look at the front value without removing it.

How it actually works

an array + two indices

Take an array and keep two indices instead of a stack's one: front (the slot to leave from) and rear (the last slot filled). Both start at -1 when the queue is empty.

  • To enqueue, move rear up one and write there: items[++rear] = val. If the queue had been empty, point front at index 0 as well.
  • To dequeue, read items[front] and then move front up one: items[front++]. The value that was there is now behind front, so it's no longer part of the queue.

Each operation touches one index and one slot — no shifting — so both are O(1). Watch both indices move as values join and leave:

 

The catch: dead space

why this simple version wastes room

Look closely at what dequeue does. It moves front to the right, but it never reclaims the slot it left behind. After a few dequeues, the slots at the far left sit there occupied by old, dead values that the queue can never reuse — because front only ever moves forward.

So when rear reaches the last slot, this array queue reports itself full — even if half the slots at the front are free. It's like a line painted on the floor: once the back of the line reaches the wall, no one else can join, even though the front of the line has emptied out.

This flaw is the whole reason the next structure exists. The Circular Queue fixes it by letting rear and front wrap around to index 0 when they hit the end — so the freed front slots get reused and no space is wasted. Read this page first, then that one; the circular version will make immediate sense.

The other common fix is to back the queue with a linked list that keeps both a front and a rear node pointer. Enqueue attaches a node after rear; dequeue detaches front. There's no fixed capacity and no dead space, at the cost of a pointer and an allocation per item.

The one gotcha. A naive "fix" for dead space is to shift every remaining element one slot left after each dequeue. Don't — that turns an O(1) dequeue into an O(n) one, and doing it on every removal is exactly the performance trap a queue is supposed to avoid. Wrap the indices (circular) or use linked nodes instead.

Where you'll meet queues. Anywhere work must be handled in arrival order: print spoolers, task and job schedulers, message queues between services, keyboard input buffers, and breadth-first search, which explores a graph in the exact order it discovers nodes — a queue is what makes BFS "breadth-first" instead of depth-first.
