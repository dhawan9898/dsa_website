Cheapest Route, One Sure Step At A Time

Dijkstra’s Algorithm

Shortest paths on a weighted graph — where edges have costs and you want the cheapest way from a start to everywhere else.

Overview Shortest Path Playground

The idea, in one picture

Plain BFS finds the route with the fewest edges — but that isn't always the cheapest. A two-hop road of 1 + 1 kilometres beats a one-hop highway of 5. When edges carry a weight (a distance, a price, a time), you want the path with the smallest total — and that's what Dijkstra's algorithm computes: the cheapest cost from one start vertex to every other.

The strategy is greedy. Keep a tentative "best cost so far" for every vertex (starting at 0 for the source and ∞ for the rest). Then repeatedly do the one thing you can be certain about: among all vertices you haven't finalized, the one with the smallest tentative cost can't possibly be improved later — so lock it in, and use it to relax its neighbours.

"Relax" an edge. To relax the edge from u to a neighbour v means: check whether going through u is cheaper than v's current best — dist[u] + weight < dist[v]. If so, update dist[v]. Every improvement to a path is just one relaxation.

Why "smallest tentative cost is final"

the one insight the whole algorithm rests on

Here's the leap. Say the un-finalized vertex with the smallest tentative cost is v, at cost d. Could some other route reach v more cheaply? That route would have to pass through some other un-finalized vertex first — but every un-finalized vertex already costs at least d to reach (that's why v was the smallest). And since weights are never negative, adding more edges only makes it costlier. So no cheaper route exists: d is final. That guarantee is exactly why Dijkstra can commit to one vertex per round and never look back.

Going deeper

costs, caveats, and where it's used
StepWhat it doesTime
Extract-minTake the cheapest un-finalized vertex (a heap)O(log V)
Relax an edgeMaybe lower a neighbour's cost, update the heapO(log V)
Whole runEvery vertex extracted, every edge relaxed onceO((V + E) log V)

The engine underneath is a priority queue (min-heap): it hands you the smallest-cost vertex each round in O(log V), which is the whole reason Dijkstra is efficient rather than O(V²).

Negative weights break it. The "smallest tentative is final" guarantee assumes extra edges only add cost. A negative edge could make a longer route cheaper after you've already finalized a vertex — so Dijkstra can be wrong. For negative weights you need Bellman–Ford instead.

Where you'll meet it. GPS and map routing (weights = travel time), network routing protocols (link cost), flight/fare finders, and any "cheapest way from here to there" over a weighted network. It's the weighted generalization of BFS, and a cousin of MST algorithms that also greedily pick the cheapest option each step.
