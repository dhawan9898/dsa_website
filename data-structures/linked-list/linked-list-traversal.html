The walk is the whole language

An array lets you jump straight to element 500 — it computes where that slot sits in memory and lands there instantly. A linked list can't. Its nodes are scattered wherever the computer found room, and the only thread connecting them is the chain of next pointers. So to reach anything past the head, you have no choice but to walk: hop from node to node, one next at a time.

That walk has a shape you'll write hundreds of times. Learn it once and every other operation becomes obvious, because insertion, deletion, and search are all just "this walk, but stop somewhere and do something":

The traversal pattern. Put a temporary pointer cur on the head. While cur isn't NULL, do whatever you came to do, then advance with cur = cur->next. The loop ends the moment cur becomes NULL — that's the list telling you "there's nothing after this; you've reached the end."

Two things make this safe. First, we walk a copy of the head (cur), never HEAD itself — move HEAD by accident and you'd lose the whole list. Second, we test for NULL before touching a node, so we never read off the end of the chain.

1 · Traverse (visit every node)

O(n) — the pure walk

Traversal is the pattern with nothing extra bolted on: visit each node in order, front to back. Here "visit" just means read and print the value, but it could be anything — sum them, find the biggest, draw them on screen.

  1. Point cur at the head.
  2. Is cur NULL? If yes, you're done — the list is fully walked. If no, carry on.
  3. Do the work on cur (here: print its value).
  4. Advance: cur = cur->next. Go back to step 2.

You touch every node exactly once, so traversal is O(n) — and it's the reason so many linked-list operations are O(n): reaching a spot is a traversal.

2 · Search (find a value)

O(n) — walk, but stop early on a match

Search is traversal with a question at each stop: is this the value I want? If yes, you're done immediately — no need to walk the rest. If you fall off the end (cur hits NULL) without ever matching, the value simply isn't in the list.

  1. Walk cur from the head as usual.
  2. At each node, compare its value to your target. Match? Return this node right away.
  3. Reached NULL with no match? Return "not found."

Best case, it's the head and you stop after one look. Worst case, it's the last node or absent, and you scan all n. On average you check about half the list — still O(n). A linked list has no shortcut like binary search, because you can't jump to the middle to begin with.

3 · Update (change a node's value)

O(n) to reach it, O(1) to change it

Updating means changing the value inside a node while leaving the node — and every pointer around it — exactly where it is. This is the one operation where you walk to the target and stop on it, not before it, because it's the target's own field you're overwriting.

  1. To update index k, walk cur forward exactly k steps. That lands you on the node at index k itself.
  2. Overwrite its value: cur->val = newValue. No pointers change; no memory is allocated or freed.

Reaching index k is a walk, so O(n); the overwrite is a single assignment, O(1). (To update by value instead of by index, first search — section 2 — then overwrite the node it returns. Same walk, same cost.)

4 · Bonus: counting the nodes

the same walk, tallying as it goes

Want the length of the list? A plain linked list doesn't store it — so you traverse and count. It's the exact same pattern with a tally added, which is the whole point of this page: once the walk is second nature, new operations are a one-line change to it.

(Many real implementations keep a size field updated on every insert and delete, so length becomes an O(1) lookup instead of an O(n) walk — a classic trade of a little bookkeeping for a lot of speed.)
