Route Around, Then Remove

Deletion

Deleting a node is a two-move dance: first make the list flow around the node, then hand its memory back. Miss either move and you get a bug.

The one idea behind every deletion

Deletion is insertion run backwards. If inserting was "clip a new car into the chain," deleting is "unclip a car and lift it out." And just like insertion, you never shift or renumber anything — you only touch the couplings around the one node you're removing.

There's exactly one node you truly need to reach to delete something, and it's easy to get wrong: it's the node before the one you're deleting — the predecessor. That predecessor is currently pointing at your victim; your job is to make it point at whatever the victim points at instead. Once you do, nothing in the list refers to the victim anymore — the list flows straight past it.

The two-move rule. First unlink: reroute the predecessor's pointer around the node. Then free: return that node's memory to the system. Order matters and so does not skipping the second move — in C, the memory a deleted node used isn't reclaimed automatically. Forget to free it and it sits there occupied but unreachable forever: a memory leak. (See the Pointers and Arrays & Memory pages for what "the memory" really is.)

As with insertion, the four flavors below differ only in how far you walk to find the predecessor. The removal itself is always the same two moves.

1 · Delete the head

O(1) — the fast one

The head has no predecessor — the HEAD pointer itself plays that role — so this is the quickest deletion. You just move HEAD forward one node and free the old first node.

  1. If the list is empty, there's nothing to delete — stop right away.
  2. Save the current head in a temporary pointer. If you skip this, the moment you move HEAD you'll have no way to reach the old node to free it — instant memory leak.
  3. Move HEAD to the second node. The old head is now bypassed.
  4. Free the old head. The list is one shorter, and no node moved.

No walking, a fixed handful of pointer moves — O(1), constant time.

2 · Delete the tail

O(n) — the predecessor is hiding at the end

To delete the last node, you need the second-to-last node — that's the predecessor whose pointer has to change from "points at the last node" to "points at NULL." And a singly linked list can't hand you that node directly; you have to walk to it.

The subtle part. You don't walk until cur->next is NULL (that would land you on the last node — too far). You walk until cur->next->next is NULL, which stops you one earlier, on the second-to-last node.

  1. Empty list? Nothing to do. Single node? That node is the head and the tail — free it and set HEAD to NULL.
  2. Otherwise walk a finger until the node two ahead is NULL. You'll land on the second-to-last node.
  3. Free the last node, then set the second-to-last node's next to NULL. It's the new tail.

Finding the predecessor means walking almost the whole list, so this is O(n).

3 · Delete at a specific index

O(n) — walk to the predecessor, route around

Same idea, general case. To delete index k, stop the walk at index k−1 — the predecessor — then let it reach over the victim to grab the victim's next.

  1. If the index is 0, that's the "delete head" case from section 1.
  2. Otherwise walk a finger to index k−1.
  3. Call the victim target — it's the predecessor's current next. Point the predecessor's next at target->next, so the list routes around target.
  4. Free target. Gone.

4 · Delete by value

O(n) — search and delete in one walk

Often you don't know the index — you just want to remove "the node that holds 7." Now you have to search for it, and the classic technique is to walk two pointers at once: cur (the node you're examining) and prev (the one right behind it). That way, the instant cur lands on a match, prev is already sitting on the predecessor you need.

  1. Walk cur from the head, dragging prev one step behind, until cur's value matches — or you fall off the end at NULL.
  2. Fell off the end? The value isn't in the list — nothing to delete.
  3. Matched at the head (prev is still NULL)? Move HEAD past it. Otherwise point prev->next around cur.
  4. Free cur.

The prev-behind-cur pattern is worth memorizing — it shows up in almost every "find and remove" on a singly linked list.

Getting it wrong (and how to not)

Freeing before rerouting. If you free the victim first and then try to read its next to reroute, you're reading memory you just gave away — a dangling-pointer bug. Unlink first (grab target->next while the node is still valid), then free.

Forgetting to free at all. Rerouting alone makes the node unreachable, but its memory is still checked out. That's a leak — invisible until your program slowly eats all its memory.

Using the pointer after freeing. After free(x), the pointer x still holds an address, but that address is no longer yours. Reading or writing through it is undefined behavior — the bug that corrupts something unrelated three functions later.

The empty-list and single-node cases. Every deletion should answer "what if the list is empty?" and tail/value deletion should also answer "what if there's exactly one node?" These edges are where real code crashes.
