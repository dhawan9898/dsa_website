Insertion

The one idea behind every insertion

Picture the list as a paper chain, or a line of train cars coupled front to back. Each node is one car; the coupling on the back of each car is its next pointer — it clips onto the car behind it. The engine at the very front is the HEAD pointer: it doesn't hold a value, it just tells you which car is first. The last car's coupling clips onto nothing, and we write that "nothing" as NULL.

An array is the opposite: its elements sit shoulder to shoulder in one solid block, so to slide a new one into the middle you must physically shove everything after it over by one — slow, and more work the bigger the array gets. A linked list never shifts anything. To insert a car, you unclip one coupling and re-clip it through the new car. That's the whole trick, and it's the same trick at the head, at the tail, and in the middle — only which coupling you touch changes.

The golden rule of insertion. Always link the new node to the rest of the list before you make anything point to the new node. Do it in the other order and, for a heartbeat, nothing points at the rest of the list — and a linked list that loses its thread can never find those nodes again. Every bug below comes from breaking this one rule. (New to pointers? The Pointers page explains what "points to" actually means in memory.)

There are three places you can insert, and they differ only in how much walking you do to reach the spot. Once you're there, the rewiring is identical. Let's take them one at a time.

1 · Insert at the start (the head)

O(1) — the fast one

This is the easiest insert and the fastest, because the head is the one node you can reach instantly — the HEAD pointer already holds its address. You never walk anywhere.

The thought process. You want your new node to become the first car in the line. So the new node's next should point at whoever used to be first, and then HEAD should be moved to point at the new node. Notice the order — it's the golden rule in action:

  1. Make a new node and put your value in it. Right now it points nowhere.
  2. Point the new node's next at the current head (the old first car). Now the new node is clipped onto the front of the existing chain — but HEAD hasn't moved yet, so nothing points at the new node.
  3. Move HEAD to the new node. It's now officially first. Nothing else in the list moved a muscle.

Because there's no walking and no shifting — just two pointer writes — this takes the same tiny amount of time whether the list holds 2 nodes or 2 million. That's what O(1), or "constant time," means. (The Big-O page unpacks that notation.)

2 · Insert at the end (the tail)

O(n) — you have to find the end first

Adding to the end sounds just as easy, and the rewiring is — but there's a catch that trips up every beginner: a plain linked list has no idea where its end is. All it knows is the head. The last node is just the one whose next happens to be NULL, and the only way to find it is to start at the head and follow the couplings, car by car, until you reach the one that clips onto nothing.

The thought process. Walk a temporary "finger" pointer from the head. At each node ask a single question: is your next NULL? If yes, this is the last node — attach the new node here. If no, step the finger forward and ask again.

  1. Handle the empty list first: if there's no head at all, the new node simply becomes the head. (Always ask "what if the list is empty?" — it's the edge case that crashes real code.)
  2. Otherwise start a finger at the head and walk: while the current node's next isn't NULL, move forward. When the loop stops, the finger is resting on the last node.
  3. Point that last node's next at the new node. The new node's own next is NULL — it's the tail now.

Walking to the end touches every node once, so the cost grows with the length of the list: that's O(n), "linear time." This is the price of a singly linked list. The common fix is to keep a second pointer, tail, that always aims at the last node — then tail insertion becomes O(1) too, at the cost of updating that extra pointer on every change.

3 · Insert at a specific index

O(n) — walk partway, then splice

"Index" just means position counted from the front, starting at 0: index 0 is the head, index 1 is the second node, and so on. Inserting at index k means the new node should end up sitting in that slot, pushing everything from k onward one place later.

The key realization. To splice a node into position k, you don't stop at index k — you stop at the node just before it, index k−1. That predecessor is the one whose coupling you'll unclip and re-route through the new node. (Inserting at index 0 has no predecessor, so it's just the head insertion from section 1 — always spot that shortcut.)

  1. If the index is 0, hand off to "insert at head" and you're done.
  2. Otherwise walk a finger to index k−1, the node just before the target slot.
  3. Point the new node's next at whatever the predecessor currently points to (that's the node being pushed back). Golden rule: this link goes first.
  4. Now re-point the predecessor's next at the new node. The new node is spliced in; the two ends of the old coupling now run through it.

You walk about k steps to reach the spot (O(n) in the worst case), but the splice itself is two pointer writes — O(1). No element after the insertion point ever moves; only the arrows change.

Getting it wrong (and how to not)

Rewiring in the wrong order. The number-one bug is doing the golden rule backwards — pointing the predecessor at the new node before the new node points at the rest. The instant you do that, the predecessor's old next is lost, and with it every node after the insertion point. The chain is severed and those nodes are unreachable forever.

Forgetting the empty list. Tail and index inserts both assume there's a head to walk from. If the list is empty, there's no node to walk, and code that blindly reads head->next will crash. Handle "empty" as its own first case.

Off-by-one on the index. Stopping at index k instead of k−1 inserts the node one slot too late. When in doubt, say out loud: "I need the node before the gap."
