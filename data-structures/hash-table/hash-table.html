Hash Table

Turns a key into an array index with a hash function, giving average O(1) insert, delete, and search.

Notes

A hash table runs every key through a hash function that turns it into a number, then uses that number (modulo the table's capacity) as an index straight into an array of buckets. If the hash function spreads keys evenly, most buckets end up with zero or one entries, and looking a key up is just "compute its hash, jump to that bucket" — O(1) on average, no searching required.

Two different keys can hash to the same bucket — a collision — and with enough keys, they will. This visualizer resolves collisions with chaining: each bucket holds a small linked list, and a colliding key just gets appended to it. (The alternative, open addressing, probes for a different empty slot elsewhere in the array instead.)

OperationAverageWorst case
InsertO(1)O(n) — one giant chain
DeleteO(1)O(n)
SearchO(1)O(n)

This is the mechanism behind every language's built-in dictionary/map/object type (Python's dict, JavaScript's Object/Map, Java's HashMap) and behind database indexes built for fast exact-match lookups.

Implementation: the code panel below backs each bucket with Node *buckets[CAP] — a fixed-size array of chain heads, no bucket array resizing. Insert walks a bucket's chain once to reject a duplicate key, then attaches the new node at whichever end that walk stopped: the bucket pointer itself if the chain was empty, or the old tail's next if it wasn't. Delete and search both walk the same chain with strcmp, comparing whole keys rather than just their hashes — the hash only narrows which bucket to search, it never confirms a match by itself.

When it breaks: this demo's hash function is deliberately weak — it just sums character codes, so anagrams like cat and act hash identically and always collide, exactly what the demo below shows. A real hash function needs to mix a key's bytes (position included) so anagrams and near-duplicates scatter across buckets instead of piling into one. The other classic failure is never resizing: even with a good hash function, a fixed CAP means chains grow steadily longer as more keys arrive, and O(1) quietly degrades toward O(n). Production hash tables watch the load factor (entries ÷ capacity) and, once it crosses some threshold, allocate a bigger bucket array and rehash every existing key into it.
