Key → Bucket, In One Step

Hash Table

A structure that turns a key straight into an array index with a bit of arithmetic — so lookups don't search, they jump.

Overview Insert Search & Delete Playground

The idea, in one picture

Imagine a wall of numbered mailboxes. To file a letter you don't search — you run the person's name through a rule that spits out a box number, and drop it straight in. To fetch it later you run the same rule, get the same box number, and open that one box. No scanning the wall. A hash table works exactly like that: it stores key–value pairs in an array of "buckets," and a hash function is the rule that turns a key into a bucket index.

The simplest hash for integer keys is key % M (the remainder when dividing by the number of buckets M) — it always lands in 0 … M-1. Because computing the index is just arithmetic — no searching — insert, look-up, and delete are all O(1) on average. That "jump straight to it" speed is why hash tables are everywhere.

The catch: collisions. Different keys can hash to the same bucket (17 and 22 both give % 5 = 2). That's unavoidable — you have infinitely many possible keys and only M buckets. So a hash table needs a plan for when two keys want the same box.

Handling collisions: chaining

each bucket holds a little linked list

The approach shown here is separate chaining: each bucket isn't a single slot but the head of a linked list. Keys that collide simply get added to that bucket's chain. Insert prepends to the chain (O(1)); search and delete hash to the bucket and then walk only that one short chain, never the others. Watch three keys collide into one bucket:

Going deeper

load factor, and where hash tables show up
OperationAverageWorst case
InsertO(1)O(n)
SearchO(1)O(n)
DeleteO(1)O(n)

Why two columns? If the hash spreads keys evenly, every chain stays short and operations are O(1). But if the hash is bad — or the table gets too full — keys pile into a few buckets and those chains grow toward length n, dragging operations to O(n). The health metric is the load factor = items ÷ buckets; once it climbs past ~0.75, real implementations resize (allocate a bigger array and re-hash everything) to keep chains short. That resize is occasionally expensive but rare, so the average stays O(1).

Beyond chaining. The other big collision strategy is open addressing: keep one item per bucket, and on a collision probe forward to the next free slot. No chains, better cache behaviour, but trickier deletes. Either way the headline idea is the same — hash the key to jump close to its home.

Where you'll meet hash tables. They back dictionaries / maps / objects in nearly every language (Python dict, JS objects, Java HashMap), database indexes, caches, de-duplication, counting unique things, and set membership tests. When code needs "look this up by name, fast," it's almost always a hash table underneath.
