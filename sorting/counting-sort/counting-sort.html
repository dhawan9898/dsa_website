Counting Sort

No comparisons at all: tally how many of each value there are, and use those tallies to place everything directly.

Overview Playground

The idea, in one picture

Every sort so far compares pairs of values. Counting sort doesn't compare anything. If your values are small whole numbers, you can just count how many times each one appears, and then read the counts back out in order. Sorting exam scores 0–100? Tally how many students got each score, then list score 0's, then score 1's, and so on. The tally is the sorted order.

Beating O(n log n). Comparison sorts can't do better than O(n log n) — that's a proven limit. Counting sort sidesteps it by not comparing: it runs in O(n + k), where k is the range of values. When k is small (scores, ages, bytes), that's effectively linear — faster than any comparison sort.

Going deeper

cost, stability, and limits
StepWhat it doesTime
TallyOne pass over the inputO(n)
Prefix sumsOne pass over the countsO(k)
PlaceOne pass placing each valueO(n)
TotalNon-comparisonO(n + k)

When it wins — and when it doesn't. Counting sort is brilliant when values are integers in a small range. But if k is huge (say 32-bit values), count[] would need billions of slots — so it only makes sense when k is comparable to n. It needs O(n + k) extra space, and it's stable if you place from right to left using the prefix sums (equal values keep their order), which is exactly what makes it the engine inside radix sort — counting sort applied one digit at a time to handle large numbers.
