Halve the Range Every Step

Binary Search

On sorted data, you can find anything by repeatedly checking the middle and throwing away half — a few steps handle a million items.

Overview Playground

The idea, in one picture

Guess a number I'm thinking of between 1 and 100. Guess 50 — I say "higher." Now you know it's 51–100, and you guess 75. Each guess halves what's left, so you corner any number in about 7 tries, not 100. That's binary search: on a sorted array, check the middle element; if it's the target you're done, and if not, the comparison tells you which half to keep — the other half is thrown away entirely.

Sorted is non-negotiable. The whole trick relies on "if the middle is too small, everything to its left is too small." That's only true if the array is sorted. On unsorted data you must fall back to linear search.

Going deeper

RequirementArray must be sorted—

Why lo + (hi − lo)/2, not (lo + hi)/2? On huge indices, lo + hi can overflow an int; the first form computes the same midpoint without ever overflowing. And the loop condition is lo <= hi (not <) so a range of one element is still checked. These two off-by-one details are the classic binary-search bugs.

Log-time is transformative: a billion sorted items take about 30 comparisons. When you'll search the same data many times, sorting once and binary-searching beats linear search enormously — jump search (O(√n)) is a simpler middle ground.
